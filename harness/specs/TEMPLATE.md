# XX-0000 — <title>

## Why

What is wrong now, and what evidence says so. Numbers where they exist. If the change is smaller than
it sounds, say so here — a spec that oversells itself produces a commit message that oversells
itself.

## Requirements

Number them. Each must be checkable by a test, and each should fail for exactly one reason.

- **R1** — …
- **R2** — …

Include at least one **negative twin**: a requirement that fails if the implementation is too
aggressive. "The signal no longer escalates" is also satisfied by deleting the signal, so pair it
with "the signal still escalates when it should".

## Scope notes

Anything a reasonable agent would fix while passing through, but that belongs to a different change.
Say why it is out of scope, so nobody has to guess.

## How this is checked

`make verify SPEC=XX-0000`.

If the change has no implementation yet, add an `oracle.py` exposing
`expected(*, apply_rule: bool = True)`. `make golden` requires `expected(apply_rule=False)` to
reproduce the library exactly before it writes the file, so the golden becomes a prediction the
implementation must meet rather than a recording of whatever the code already did. Without an oracle,
the golden can only record current behaviour.

Files in a spec directory:

| File | Purpose |
| --- | --- |
| `SPEC.md` | this document; front matter drives the gate |
| `corpus.json` | fixed inputs — synthetic only, never real data |
| `product.py` | `product()` returning the canonical observable output |
| `oracle.py` | optional; `expected()` predicting the product |
| `golden.json` | generated by `make golden SPEC=XX-0000` (maintainer) |
| `test_acceptance.py` | one test per requirement |
